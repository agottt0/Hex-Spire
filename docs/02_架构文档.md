# Hex Spire 架构文档

> 面向新加入者与未来的自己。读完这份应该知道：代码分几层、为什么这么分、改一个功能该动哪个文件、哪些地方绝对不能碰。
>
> 玩法规则的真相来源是 `docs/00_系统策划案.md`。本文只讲**代码结构**。

---

## 1. 一句话架构

**逻辑层瞬时算完，表现层按事件流回放。**

```
玩家点击 ──▶ BattleFlow ──▶ ActionQueue ──▶ ActionResolver ──▶ BattleState 改变
																	 │
														  追加纯数据到 event_log
																	 │
			 battle_scene 每帧 drain ◀──────────────────────────────┘
					 │
					 └──▶ EventBus 信号 ──▶ UnitView / CardView 播动画
```

关键性质：**逻辑不等待动画**。一次 `play_card()` 返回时战斗状态已经全部算完，动画只是事后回放。这带来三个直接红利：

- 战斗能在**无渲染**下跑完 → `battle_sim` / 平衡矩阵 / 全部验证器成立
- "一键跳过动画" = 把 `K.EVENT_PLAYBACK_INTERVAL` 设成 0
- 确定性可验证：同 seed 两次运行的 `action_log` 哈希逐位相同

## 2. 目录与分层

严格遵循策划案 §14.1，未自创结构。

```
src/
├── autoload/          全局单例（3 个）。⚠️ core 不许引用
│   ├── event_bus.gd       只声明 signal + dispatch()，零逻辑
│   ├── database.gd        启动时扫描 data/ 建索引
│   └── rng_service.gd     RngStreams 的持有者
│
├── core/              ⚠️ 纯逻辑层：零 Node 依赖、可序列化、可无渲染跑完
│   ├── enums.gd           所有共享枚举的唯一定义处
│   ├── constants.gd       class_name K —— 所有可调数值
│   ├── hex/               六边形几何（4 文件，约 900 行）
│   │   ├── hex_coord.gd       ⭐ 坐标转换唯一出口
│   │   ├── hex_footprint.gd   ⭐ 体型占位校验唯一出口
│   │   ├── hex_grid.gd        7×7 格子容器
│   │   └── hex_pathfinder.gd  (anchor, facing) 状态图寻路
│   ├── battle/            战斗逻辑（20 文件，约 3500 行）
│   ├── deck/              牌堆循环（2 文件）
│   ├── rng/rng_streams.gd 注入式 RNG（5 条独立流）
│   ├── map/ loot/ runes/  预留目录（P4/P6）
│   └── net/               D7 空壳，不实现
│
├── scenes/            表现层：只订阅事件、只发送输入（约 1100 行）
│   └── battle/
│       ├── battle_scene.gd     场景入口，drain event_log
│       ├── hex_board_view.gd   ⭐ 唯一接触 TileMapLayer 的文件
│       ├── greybox_tileset.gd  运行时生成六边形贴图（零美术文件）
│       ├── unit_view.gd        footprint 描边 + 接地阴影 + 朝向
│       └── ui/card_view.gd     纯色 Panel + 文字
│
tools/                 验证器与调试工具（约 1900 行，全部 headless）
data/                  .tres 资源目录（当前内容在 content_library.gd 里）
docs/                  策划案 / 美术高概念 / 本文
```

**为什么 `core/` 和 `scenes/` 要硬隔离**：这是策划案 §12.1 纪律 3 的要求，也是全部自动化验证的前提。若 core 里出现一个 `await`，`battle_sim` 就跑不起来，10 万场模拟与平衡矩阵全部失效。

## 3. 五条架构纪律（§12.1）—— 由 CI 机械强制

`tools/check_discipline.gd` 扫描源码，命中即失败。这是全项目性价比最高的检查：它把 review 从"逐行找问题"变成"看退出码"。

| 纪律 | 内容 | 强制方式 |
|---|---|---|
| **1 注入式 RNG** | 禁止 `randi()` / `randf()` / `Array.shuffle()` / `pick_random()`。RNG 通过构造参数注入 | 正则扫描 `core/`，`rng.xxx()` 形式豁免 |
| **2 状态变更走 ActionQueue** | 禁止在表现层写 `unit.hp -= x`。所有变更转成 `GameAction` | 扫描 `scenes/` 的直改模式 |
| **3 表现层分离** | `core/` 禁止 `await` / `get_tree()` / `extends Node` / 引用 autoload | 正则扫描 |
| **4 按单位集合设计** | `Unit` 是粒度，不假设我方只有 1 个（为召唤物预留） | 人工 review |
| **5 完全确定性** | 禁止读系统时间、禁止依赖 Dictionary 遍历顺序做逻辑判断 | 正则 + `--verify-determinism` 哈希比对 |

额外的两条白名单强制：
- `local_to_map` / `offset_to_map` 只允许出现在 `hex_coord.gd` 与 `hex_board_view.gd`
- `GameRule.XXX` 只允许出现在 `enums.gd` / `rule_book.gd` / `rune_loadout.gd` / 数据声明文件；读取规则值必须走 `RuleBook`

## 4. 关键设计决策

### 4.1 单一出口原则

三个"唯一出口"，绕过它们就是 bug：

| 出口 | 职责 | 绕过的后果 |
|---|---|---|
| `HexCoord` | 所有坐标转换与旋转 | 坐标系不一致，网格错位（见 §6 的两个陷阱） |
| `HexFootprint.can_place()` | 体型占位校验 | R9：多格单位的边界情况极多，后期加体型系统重构成本极高 |
| `RuleBook.xxx()` | 读取被符文改写后的规则值 | 规则读取散落十几处，符文改写失效 |

### 4.2 GameAction：扁平数据 + 处理器注册表

不用子类多态，用 `{type: StringName, data: Dictionary}`。

**代价**：字段没有静态类型 → 用 `actions.gd` 的命名构造器补偿。
**收益**：`to_dict()/from_dict()` 各两行 → 动作日志天然是 JSON，于是战报、Undo、bug 复现、（未来的）联机广播全部免费。

`ActionResolver` 是**唯一**能修改 `BattleState` 的地方，19 种动作各一个处理器。

### 4.3 push_next vs push_back

```gdscript
queue.push_back(a)   # 排到队尾
queue.push_next(a)   # 插到【当前动作之后】
```

`push_next` 是必须的：符文触发的子动作要紧随触发者结算，否则 §6.5 的"槽位 1→6 顺序"会被打乱——槽 1 的子动作会跑到槽 6 的主动作后面。

### 4.4 伤害管线的 ②′ 顺序钩子

§4.4 要求"加法全做完再乘"，§6.5 要求 `[锐化,倍化] ≠ [倍化,锐化]`。两条冲突：桶式聚合会让顺序失效，D6 的深度归零。

解法是在 ② 与 ③ 之间开一个**顺序敏感**阶段：

```
① flat + stat×ratio  →  ② 非符文平坦加成  →  ②′ 符文按槽位依次 += / *=
→ ③ 非符文乘区  →  ④ 暴击  →  ⑤ 减伤  →  ⑤′ 取整+下限  →  ⑥ 扣格挡
```

实测：ATK=10 时 `[锐化,倍化] = (10+5)×1.4 = 21`，`[倍化,锐化] = 10×1.4+5 = 19`。

**⑤′ 在 ⑥ 之前是有意偏离策划案字面顺序**：按字面（下限在扣格挡后）会让格挡永远无法完全吸收伤害，骑士的"格挡不清空"被动失去意义。

### 4.5 calculate / preview 双入口

`preview()` **不接受 rng 参数**。若预览走同一函数，鼠标悬停就会消耗 RNG → 污染确定性并打爆 Undo 的撤销屏障。

### 4.6 意图必须是"承诺"

`EnemyAI.decide()` 在生成意图时**冻结全部结算参数**（目标格集合 / 伤害包），`execute_intent()` 只重放。这是"打空型 vs 追踪型"能区分的前提，而 §13.2 明确要求玩家能读出「意图是否可躲」。

两段明示规则：
- 贴身（`dist <= 1`）近战 → 转 TRACK（咬住了，躲不掉）
- 远处扑击 → FIXED_TILE，覆盖玩家占格 + 朝向侧 3 方向

### 4.7 Undo 用快照，不用逆动作

逆动作在有状态/位移/牌堆的系统里必然写错。`BattleState.snapshot()` 深拷贝约几 KB，回合制下零压力。**撤销屏障**：动作后若 `rng.draw_count` 变化、或发生信息揭示（抽牌）、或进入敌方阶段 → 清空撤销栈。

### 4.8 R7 安全闸：超限不 crash

符文组合可能死循环。三重上限（递归深度 10 / 单次 emit 触发 64 / 单次 resolve 2000 动作）超限时**写 `state.rule_violations` 并中止，绝不抛异常**——这让 `battle_sim` 能把死循环变成可统计数据而非崩溃。

## 5. 数据流：一次出牌完整走一遍

```
1. battle_scene._try_play_at_mouse()
2. BattleFlow.play_card(card, cell)
	 ├─ RuleBook.card_cost() 检查体力
	 ├─ TargetResolver.legal_cells() 检查目标合法
	 ├─ queue.push_back(Actions.spend_energy(...))
	 ├─ _execute_step() 逐个 EffectStep：
	 │    ├─ TargetResolver.affected_units()  ← 队伍过滤在这里
	 │    ├─ TriggerBus.make_value_hook(ON_ATTACK)  ← ②′ 顺序钩子
	 │    ├─ DamageCalculator.calculate(ctx, rng, hook)
	 │    └─ queue.push_back(Actions.damage(...))
	 ├─ PileManager.resolve_played_card()  → 弃牌堆 or 消耗区
	 ├─ TriggerBus.emit(ON_CARD_PLAYED)
	 └─ queue.resolve_all(state)
		  └─ ActionResolver.execute() 逐个动作
			   ├─ 改 BattleState（唯一合法位置）
			   ├─ state.log_event(...)  → event_log
			   └─ TriggerBus.emit(下游时机)  → 可能 push_next 子动作
3. battle_scene._sync_all()
	 ├─ state.drain_events() 取走事件
	 └─ 刷新 UnitView / CardView / 状态栏
```

## 6. 两个坐标系陷阱（改 `hex_coord.gd` 前必读）

### 陷阱 1：`DIRS[facing]` 不是朝向向量

`rotate()` 使 `DIRS` 索引**递减**（`DIRS[0] → DIRS[5] → DIRS[4]`）。所以 `facing=2` 的 footprint 朝上，但 `DIRS[2]` 指向 row 减小的方向（朝下）。

取朝向必须用 `HexCoord.facing_dir(facing)`，等价于 `DIRS[posmod(-facing, 6)]`。已用策划案 §8.2.4 的出生表交叉验证：**§8.1 原文的 rotate 公式是对的，不要改**。

### 陷阱 2：`MAP_Y_FLIP` 必须是偶数

业务 row 1 在**下**，Godot map y 向**下**增长，需要翻转。若翻转常数取奇数（比如 `ROWS=7`），则 `K - row` 与 `row` 奇偶性相反 → odd-r 的"奇数行右移"渲染成"偶数行右移" → **整个网格被剪切错位，且单看一格完全正常**，极难发现。

### 陷阱 3：通过性是寻路问题，不是几何问题

"某体型能否通过狭道"必须用 `HexPathfinder` 在 `(anchor, facing)` 状态图上搜索。我用静态几何试过 4 种判据全部失败（详见 `tools/verify_footprint.gd` 的注释）。

实测的三级门宽闸门：

| 门宽 | S | M | L |
|---|---|---|---|
| 1 格 | 可过 | 过不去 | 过不去 |
| 2 格 | 可过 | 可过 | 过不去 |
| 3 格 | 可过 | 可过 | 可过 |

## 7. 验证体系

全部 headless、退出码即结论。改任何东西后至少跑 `check_discipline` + 相关验证器。

| 工具 | 验证什么 |
|---|---|
| `check_discipline.gd` | 五条纪律 + 两个白名单（34 文件） |
| `verify_hex.gd` | 坐标往返、旋转闭合、facing 语义、map 奇偶性（8 项） |
| `verify_footprint.gd` | **3528 组** `can_place` 与独立参考实现比对（R9） |
| `verify_damage.gd` | 管线 7 阶段、符文顺序 21≠19、preview 不耗 RNG、R2 排序不变（6 项） |
| `verify_pathfinding.gd` | 最短路、体型闸门、确定性 tiebreak（5 项） |
| `verify_balance.gd` | 16 格矩阵：张力格 ≥6、超时 ≤1、零违规 |
| `battle_sim.gd` | 批量模拟 + R1' 重复率 + R7 违规统计 + `--verify-determinism` |
| `debug_battle.gd` | 单场逐回合诊断（查手感与 bug 的主力工具） |

⚠️ **新增 `class_name` 后必须重建类缓存**，否则 headless 脚本报「Identifier not declared」：

```bash
rm -rf .godot
"$GODOT" --headless --path . --editor --quit-after 4000
```

纯 `--import` 不够，必须走 `--editor`。

## 8. 怎么加东西

| 要加什么 | 改哪里 | 注意 |
|---|---|---|
| **一张卡** | `content_library.gd` 的 `all_cards()` | 必须走 `flat + stat_ref × ratio`（§7.5 强制系数化），禁止硬编码伤害 |
| **一个敌人** | `content_library.gd` 的 `all_enemies()` | 选对 `ai_profile` 与 `intent_targeting`（可躲/追踪） |
| **一种效果 op** | `enums.gd` 加枚举 → `battle_flow._execute_step()` 加分支 | 漏了会静默记 `unimplemented_op` |
| **一种动作** | `actions.gd` 加构造器 → `action_resolver._register()` 注册处理器 | 两处必须同步，否则 `no_handler` 违规 |
| **一个可调数值** | `constants.gd`（class_name K） | 不要散落在逻辑里 |
| **一个地形模板** | `content_library.gd` 的 `layout_*()` | 出生区不得有 hazard；需校验敌人可达玩家 |
| **一个触发时机** | `enums.gd` 的 `TriggerTiming` + 在流程里埋 `emit` | 埋点时监听者为空几乎零成本，事后回填极痛 |
